# JVM 运行时内存分布与垃圾回收策略

  <span class="question-tag">Java</span>
  <span class="question-tag">JVM</span>
  <span class="question-tag">内存</span>
  <span class="question-tag">垃圾回收</span>

> JVM 运行时内存分为哪几个区域？哪些是线程共享、哪些是线程私有？堆为什么分代、对象在新生代和老年代之间怎么流转？判断对象能否回收有哪几种方式？常见的垃圾回收算法和收集器（CMS、G1）各有什么特点、面试里怎么答？

### 一、这道题在考察什么

「JVM 内存分布 + 垃圾回收」几乎是 Java 面试的**必考题**，但它从来不是单独问「背一下有哪些区」。面试官真正想顺着这条线摸清三件事：

1. **基础是否扎实**：运行时数据区一共几块，能不能分清「线程共享」和「线程私有」，这是送分题，答错直接印象分拉低。
2. **有没有被 JDK 版本坑过**：永久代（PermGen）在 JDK 8 被元空间（Metaspace）取代，还死背「方法区就是永久代」的人，暴露的是没跟上版本演进。
3. **会不会关联实际故障**：OOM、`OutOfMemoryError`、频繁 Full GC 调优，都建立在对堆结构和 GC 机制的理解上——答到「怎么定位、怎么调」才拿得到高分。

所以这篇文章按「**结构 → 流转 → 回收**」三层展开，最后落脚到面试怎么组织答案。

### 二、运行时数据区：先分清「共享」与「私有」

JVM 的内存区域可以一刀切成两大类：**所有线程共享**的，和**每个线程私有**的。

<div class="diagram-card">
  <img src="../../assets/diagrams/jvm-memory-gc/runtime-data-areas.svg" alt="JVM 运行时数据区：线程共享的堆和方法区，线程私有的虚拟机栈、程序计数器、本地方法栈，以及堆的分代结构">
</div>

#### 线程共享（全局只有一份）

| 区域 | 存什么 | 备注 |
|------|--------|------|
| **堆（Heap）** | 所有 `new` 出来的对象实例和数组 | GC 的主战场，也是 OOM 高发区 |
| **方法区 / 元空间（Metaspace）** | 类信息、常量、静态变量、JIT 编译后的代码 | JDK 8 起**移出堆**，改用本地内存 |

> **JDK 8 的关键变化**：永久代（PermGen）被移除了，取而代之的是**元空间（Metaspace）**，使用**本地内存（Native Memory）**而非堆内存。好处是默认不再受 `-XX:MaxPermSize` 那个固定上限约束，坏处是如果类加载器没被正确卸载，元空间也可能把本地内存撑爆。

#### 线程私有（每个线程各一份）

| 区域 | 存什么 | 备注 |
|------|--------|------|
| **虚拟机栈（VM Stack）** | 一个个「栈帧」，栈帧里有局部变量表、操作数栈、方法返回地址等 | 每调一个方法压一个栈帧 |
| **本地方法栈（Native Stack）** | `native` 方法调用 | HotSpot 里和虚拟机栈已合并 |
| **程序计数器（PC Register）** | 当前线程正在执行的字节码指令地址 | **唯一不会抛 OOM 的区域** |

> 记忆锚点：**「栈」管方法调用（往里压栈帧），「堆」管对象数据（往里放实例）**。一个方法结束，栈帧弹出，局部变量里指向堆对象的引用也就断了，为 GC 埋下伏笔。

### 三、堆为什么分代：新生代与老年代

堆是 GC 的核心区域，HotSpot 把它进一步分成**新生代（Young）**和**老年代（Old）**，新生代里又分 **Eden + 两个 Survivor（S0、S1）**，默认比例 **8:1:1**。

分代的依据是一条经验规律——**弱分代假说（Weak Generational Hypothesis）**：

```
绝大多数对象都是「朝生夕死」——诞生后很快就不用了，
熬过一次又一次 GC 还活着的对象，往往能活很久。
```

既然两类对象的生命周期差异这么大，就把它们**分开管理、用不同的回收策略**：新生代高频回收（快、代价小），老年代低频回收（慢、代价大）。这比「整个堆无差别扫描」高效得多。

### 四、对象的一生：从 Eden 到老年代

理解了区域，再看一个对象在堆里怎么「流转」，这是 GC 机制的骨架：

<div class="diagram-card">
  <img src="../../assets/diagrams/jvm-memory-gc/object-lifecycle.svg" alt="对象流转：从 Eden 出发，Minor GC 存活进入 Survivor，年龄达阈值或放不下时晋升老年代，大对象直接进老年代">
</div>

完整流程拆开看：

1. **诞生在 Eden**：新对象都在 Eden 区分配内存。
2. **Eden 满了触发 Minor GC**：回收掉 Eden 里没人引用的对象，活下来的进入 Survivor（S0 或 S1），年龄记为 1。
3. **S0 ↔ S1 来回倒腾**：之后每次 Minor GC，存活对象在两个 Survivor 之间**复制搬运**，每搬一次年龄 +1（这就是「复制算法」的体现，也解释了为什么是两个 Survivor）。
4. **晋升老年代**：当对象年龄达到阈值（默认 **15**，对应 `-XX:MaxTenuringThreshold`），或者 Survivor 实在放不下时，晋升到老年代。
5. **大对象直通老年代**：超过阈值的大对象（如大数组、大字符串）会**绕过新生代直接进老年代**，避免在 Eden/Survivor 里反复复制。

> 关键记忆点：**新生代用「复制」算法（留一半空着来回倒），老年代用「标记-整理/清除」算法**——因为老年代对象存活率高，没有「大量死亡对象」可高效复制，也腾不出「空闲一半」的空间。

### 五、判断对象能否回收：两种方式

GC 的第一步不是「回收」，而是「找出哪些对象已经死了」。主流有两条路：

| 方式 | 思路 | 评价 |
|------|------|------|
| **引用计数法** | 每个对象记一个「被引用次数」，归零即可回收 | 简单高效，但**解决不了循环引用**（A↔B 互相引用，计数永不为零） |
| **可达性分析**（JVM 用的） | 从一组 **GC Roots** 出发，沿引用链向下找，能到达的对象存活，到达不了的就是垃圾 | 能正确处理循环引用，是 Java 的主流方案 |

**GC Roots 有哪些**（面试常追问）：

```
GC Roots 集合：
  ├─ 虚拟机栈里引用的对象（局部变量、参数）
  ├─ 方法区/元空间中静态属性引用的对象
  ├─ 方法区/元空间中常量引用的对象
  ├─ 本地方法栈中 JNI 引用的对象
  └─ 被同步锁（synchronized）持有的对象
```

> 补充：Java 的引用类型（强/软/弱/虚）也和这里挂钩——**软引用**在内存不足时回收，**弱引用**下次 GC 就回收，常用于缓存、`WeakHashMap`、`ThreadLocal` 等场景，是可达性分析的延伸考点。

### 六、垃圾回收算法：四板斧

| 算法 | 做法 | 优点 | 缺点 | 用在哪 |
|------|------|------|------|--------|
| **标记-清除** | 标记存活对象 → 直接清除垃圾 | 简单 | 产生**内存碎片** | 老年代的基础 |
| **标记-复制** | 把存活对象复制到另一块，整块清空 | 无碎片、高效 | 浪费一半空间 | **新生代** |
| **标记-整理** | 标记 → 把存活对象**向一端移动** → 清理边界外 | 无碎片 | 移动成本高、STW 长 | **老年代**（CMS 的替代） |
| **分代收集** | 按对象年龄分区，各区用不同算法 | 兼顾效率与吞吐 | 复杂 | **现代 JVM 主流** |

> 一句话串起来：**新生代存活率低 → 用「复制」；老年代存活率高 → 用「整理」或「清除」；分代收集就是把它们组合起来各司其职。**

### 七、垃圾收集器：从 CMS 到 G1

收集器是上述算法的具体实现，面试高频的是 **CMS** 和 **G1**（以及更现代的 ZGC）。

#### CMS：以「低停顿」为目标的老年代收集器

CMS（Concurrent Mark Sweep）主打**尽可能缩短 STW**，把标记过程拆成和用户线程并发执行：

```
CMS 的四个阶段：
  ① 初始标记（STW）        —— 只标记 GC Roots 直接关联的对象，很快
  ② 并发标记（并发）        —— 和用户线程一起，遍历对象图
  ③ 重新标记（STW）        —— 修正并发期间变动的引用
  ④ 并发清除（并发）        —— 清除垃圾，不整理
```

CMS 的硬伤正是它的名字——**「Mark Sweep」用标记-清除，不整理**，会留内存碎片，碎片严重时触发一次 Full GC 兜底；而且对 CPU 敏感、需要预留空间。所以 **JDK 9 把它标记为废弃，JDK 14 直接移除**。

#### G1：面向大堆、可预测停顿

G1（Garbage First）把整个堆**划分成大量等大的 Region**，不再严格按「物理连续的新生代/老年代」划分，而是**动态地在 Region 上划分 Eden / Survivor / Old**：

| 特性 | CMS | G1 |
|------|-----|-----|
| 内存布局 | 连续分代 | **Region 化**，动态划分 |
| 核心目标 | 低停顿 | **可预测停顿时间**（`-XX:MaxGCPauseMillis`） |
| 碎片问题 | 有（不整理） | 无（局部复制/整理） |
| 特点 | 并发低停顿，但会退化 Full GC | **优先回收垃圾最多的 Region**（Garbage First 名字由来） |

G1 的另一个关键改进是**停顿可预测**：设定一个期望的最大停顿时间，G1 会**优先回收「垃圾占比最高」的 Region**，在预算时间内尽量多回收，而不是无脑全堆扫。

> 版本对照记忆：**JDK 8 默认 Parallel（吞吐优先）+ CMS 可选；JDK 9 起 G1 成为默认收集器**；再往后 ZGC（JDK 11 引入、JDK 15 转正）以「超低停顿（亚毫秒级）、可扩展到大堆」成为新一代方向。

### 八、关联 OOM：常见的几种与排查

把内存结构吃透，最终要能落到**线上故障排查**，这也是面试的加分项：

| 异常 | 常指哪里出了问题 | 排查方向 |
|------|------------------|---------|
| `OutOfMemoryError: Java heap space` | **堆**不够 | 堆内存泄漏 / 对象无节制增长，dump 分析大对象 |
| `OutOfMemoryError: Metaspace` | **元空间**不够 | 大量动态生成类（如 CGLIB 代理、反射）没卸载 |
| `StackOverflowError` | **虚拟机栈**溢出 | 无限递归、深层调用 |
| `OutOfMemoryError: unable to create new native thread` | **本地内存**不足 | 线程数超上限，栈 + 线程数需调优 |

> 排查套路：先看日志里异常类型定位是「哪块内存」→ 用 `jmap -dump` 或 JVM 参数（`-XX:+HeapDumpOnOutOfMemoryError`）抓堆转储 → 用 MAT/VisualVM 分析「谁占了大头、谁持有引用不释放」。**能说出这套「定位 → dump → 分析」的动作，比背概念更让面试官觉得你上过手。**

### 九、总结与面试答题框架

| 问题 | 答案要点 |
|------|---------|
| 运行时数据区怎么分 | 共享：堆、方法区/元空间；私有：虚拟机栈、本地方法栈、程序计数器 |
| JDK 8 关键变化 | 永久代 → 元空间，移出堆改用本地内存 |
| 堆为什么分代 | 弱分代假说：多数对象朝生夕死，分开管理更高效 |
| 对象怎么流转 | Eden → Survivor 来回倒 → 年龄到 15 晋升老年代；大对象直进老年代 |
| 判断可回收 | 引用计数（有循环引用缺陷）vs 可达性分析（GC Roots，JVM 主流） |
| 三种 GC | Minor（新生代）、Major（老年代）、Full（全堆+方法区） |
| 四大算法 | 标记-清除 / 标记-复制（新生代）/ 标记-整理（老年代）/ 分代 |
| CMS vs G1 | CMS 低停顿但留碎片、已废弃；G1 Region 化、停顿可预测、JDK 9 起默认 |

**面试组织答案的建议顺序**：先一句话框定「共享 vs 私有」的整体图景 → 讲堆的分代和对象流转（这是 GC 的地基）→ 讲可达性分析判断死亡 → 讲算法和收集器 → 最后落到「OOM 怎么定位」收尾。**从结构讲到故障排查，能串成一条完整的因果链，是这道题从「及格」到「高分」的分水岭。**
