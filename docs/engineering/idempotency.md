# 请求的幂等性如何保证

  <span class="question-tag">接口设计</span>
  <span class="question-tag">并发</span>
  <span class="question-tag">Redis</span>
</div>

> 什么是幂等性？GET / PUT / POST 哪些天然幂等？重复请求是怎么产生的（超时重试、用户连点、MQ 重投）？保证幂等的常见方案有哪些 —— Token 唯一 ID、数据库唯一索引、乐观锁、状态机、分布式锁，各自适用什么场景？为什么「先 SELECT 再 INSERT」在并发下不可靠？加了分布式锁就算幂等了吗？

### 一、什么是幂等性

**定义**：同一个请求，执行一次和执行多次，对系统产生的**副作用**完全一致。

用数学式子表达就是 `f(f(x)) = f(x)` —— 重复作用等同于一次作用。

HTTP 方法在语义上有明确的幂等约定：

| 方法 | 幂等 | 说明 |
|------|------|------|
| `GET` | ✅ | 只读，不改变服务端状态 |
| `PUT` | ✅ | 整体替换，多次提交结果一致 |
| `DELETE` | ✅ | 删一次和删多次，结果都是「资源不存在」 |
| `POST` | ❌ | 每次提交都新建资源 / 产生新副作用 |
| `PATCH` | ⚠️ | 视实现而定，部分更新可能非幂等 |

两个容易踩的坑：

- **幂等关注的是「副作用」，不是「响应内容」**。`DELETE` 第二次可能返回 404，但「资源已被删除」这个状态没变，所以仍是幂等。
- **语义幂等 ≠ 实现幂等**。HTTP 规范说 `PUT` 幂等，但你的代码要是每次 `PUT` 都往表里插一条，它照样不幂等。**幂等是服务端要保证的性质，不是协议白送的。**

### 二、为什么需要幂等：重复请求从哪来

| 来源 | 典型场景 |
|------|---------|
| 超时重试 | 客户端没收到响应，自动 / 人工重试 |
| 用户重复点击 | 按钮没做防抖，连点两次 |
| MQ 重复投递 | 消费失败、ack 超时，消息被重新投递 |
| 上游重试与补偿 | 调用方重试机制、定时任务补偿 |
| 网关 / 代理重发 | 负载均衡、网关超时后重发 |

> 核心认知：**「超时」不等于「失败」**。请求很可能已经在服务端执行成功了，只是响应在回程丢了。所以绝不能用「我没收到响应」来推断「服务端没执行」——这正是幂等要兜住的问题。

前端做按钮置灰、防抖能减少一部分重复提交，但**拦不住网络重试和 MQ 重投**，所以幂等必须在服务端做。

### 三、方案一：唯一请求 ID / Token 机制

最通用的「前置拦截」方案，核心是**用一个全局唯一的幂等号，把「第一次」和「后续次」区分开**。

流程如下：

1. 客户端在提交前（如进入下单页）先向服务端**申请一个幂等 token**
2. 服务端生成全局唯一 token，写入 Redis 并设置 TTL，返回给客户端
3. 客户端提交业务请求时，在请求头 / 参数里带上这个 token
4. 服务端收到请求，对 token 做**原子性的校验并删除**
   - 删除成功（首次）→ 放行，执行业务
   - 删除失败 / 不存在（重复）→ 直接拒绝，或返回首次的执行结果
5. 业务执行、落库

<div class="diagram-card">
  <img src="../../assets/diagrams/idempotency/token-mechanism.svg" alt="Token 幂等机制流程：申请 token、携带提交、原子校验删除、通过则执行否则拒绝">
</div>

关键点：**校验和删除必须是原子操作**。不能先 `GET` 判断存在、再 `DEL` —— 两步之间有并发窗口，两个请求可能同时 `GET` 到「存在」，于是都被放行。

```java
// Redis 原子删除：DEL 返回 1 表示删除成功（首次），0 表示 key 不存在（重复）
Long deleted = redisTemplate.delete("idem:token:" + token);
if (deleted == null || deleted == 0) {
    // 重复请求：直接返回上次结果或报错
    return Result.duplicate("请勿重复提交");
}
// 首次请求：放行执行业务
return doBusiness(request);
```

更复杂的判断（比如要区分「处理中」和「已完成」）用 Lua 脚本保证原子性：

```lua
-- KEYS[1]=token key；返回 1 放行，0 拒绝
if redis.call('DEL', KEYS[1]) == 1 then
    return 1
else
    return 0
end
```

- **适用**：创建类操作（下单、发券、充值）
- **注意**：token 要设 TTL，避免客户端申请了不用导致垃圾 key 堆积；token 生成要保证全局唯一（UUID / 雪花 ID）

### 四、方案二：数据库唯一索引（防重表）

用数据库的**唯一约束**兜底，是最可靠的「最后一道防线」。

做法：给业务表（或单独的防重表）建唯一索引，唯一键 = 业务唯一标识：

```
唯一键示例：
  order_no                       订单号
  request_id                    上游请求 ID
  user_id + biz_type + biz_id   用户 + 业务类型 + 业务 ID（如「用户A领取优惠券B」）
```

插入成功 = 首次请求；插入抛出 `DuplicateKeyException` = 重复请求，直接返回。

- **优点**：强一致、绝对可靠 —— 数据库约束不会因为缓存失效、Redis 宕机而漏防
- **缺点**：依赖 DB，高并发下有写压力；需要提前设计好唯一键
- **适用**：创建类操作，通常作为**兜底**与 Token 机制配合使用

> 工程实践里的共识：**高并发创建类接口，Token 前置拦截 + 唯一索引兜底，双保险**。前者挡掉绝大部分重复流量，后者保证极端情况下也不会产生脏数据。

### 五、方案三：乐观锁（版本号 / CAS）

适合**更新**类操作。给表加 `version` 字段：

```sql
UPDATE product
   SET stock = stock - 1, version = version + 1
 WHERE id = 100 AND version = 5;
```

- 影响行数 = 1 → 更新成功
- 影响行数 = 0 → 版本号已被别人改过（或已被处理过），拒绝 / 重试

用状态字段做条件，本质也是乐观锁：

```sql
UPDATE orders SET status = 'PAID'
 WHERE id = ? AND status = 'UNPAID';   -- 已经是 PAID 的不会被重复更新
```

- **优点**：无锁，性能好
- **缺点**：只适合更新，不适合创建；需要处理「影响行数 = 0」的情况
- **适用**：扣库存、改金额、更新状态

### 六、方案四：状态机约束

如果业务本身有明确的状态流转，直接用状态做天然幂等：

```
订单：待支付 → 已支付 → 已发货 → 已完成
```

只允许从「待支付」流转到「已支付」；重复的支付请求进来时发现已经是「已支付」，直接拒绝。

这本质上是**乐观锁的业务语义版** —— 利用业务状态的不变性做约束。

- **优点**：最自然，不需要额外字段
- **适用**：有明确状态流转的业务（订单、工单、审批流）

### 七、方案五：分布式锁 —— 它不能替代幂等

常见误解：**「我加了分布式锁，所以接口是幂等的」**。这是错的。

以业务唯一标识为 key 加锁（Redis `SETNX` / Redisson）：

```java
RLock lock = redisson.getLock("lock:order:" + orderNo);
lock.lock();
try {
    doBusiness();
} finally {
    lock.unlock();
}
```

问题在于：**锁只防「同时」，不防「先后」**。

- 请求 1 拿到锁 → 执行 → 释放锁
- 请求 2 隔了 5 秒再来 → 锁早就释放了 → 照样拿到锁 → 照样执行一遍

> 一句话区分：**分布式锁解决的是「并发下别同时执行」，幂等解决的是「多次执行结果一致」**。锁是互斥手段，不是去重手段。要幂等，仍需配合前面的 Token / 唯一索引 / 乐观锁。

### 八、为什么「先 SELECT 再 INSERT」不可靠

最常见的错误写法：

```java
// ❌ 错误示范
Order exist = orderMapper.selectByOrderNo(orderNo);
if (exist == null) {
    orderMapper.insert(order);   // 并发下：两个请求都查到 null，都插入 → 产生两条
}
```

两个请求并发进来时，**都 SELECT 到 null，于是都 INSERT**，最终产生两条记录。

除非：

- 用数据库唯一索引兜底（第二次 INSERT 直接失败）；或
- 整个「查 + 插」用锁 / 原子操作包起来（性能差，不推荐）

> 结论：**「先查后插」在并发下不可靠**，必须有原子约束兜底 —— 唯一索引、原子删除的 token、乐观锁，三选一（或组合）。

### 九、方案对比与选型

<div class="diagram-card">
  <img src="../../assets/diagrams/idempotency/strategies.svg" alt="幂等方案选型：创建类用 Token 加唯一索引，更新类用乐观锁或状态机，分布式锁只防并发">
</div>

| 方案 | 适用操作 | 关键实现 | 注意点 |
|------|---------|---------|-------|
| Token / 唯一 ID | 创建类 | Redis 原子删除 | 校验 + 删除要原子，设 TTL |
| DB 唯一索引 | 创建类 | 唯一键约束 | 提前定好唯一键，兜底最可靠 |
| 乐观锁 version | 更新类 | `WHERE version = ?` | 处理影响行数 = 0 |
| 状态机 | 有流转的业务 | 状态条件更新 | 依赖业务有明确状态 |
| 分布式锁 | 防并发 | SETNX / Redisson | **不解决先后重复** |

选型建议：

- **创建类**（下单、发券）：Token 前置拦截 + DB 唯一索引兜底
- **更新类**（扣库存、改状态）：乐观锁 / 状态机
- **有状态流转**：优先用状态机，最简洁
- **前端配合**：按钮防抖 / 置灰减少重复提交，但**不能只靠前端**

### 十、总结

| 问题 | 答案 |
|------|------|
| 幂等是什么 | 同一请求执行一次与多次，对系统的副作用一致 |
| 为什么需要 | 超时 ≠ 失败，重试 / 连点 / MQ 重投都会产生重复请求 |
| POST 幂等吗 | 不幂等，每次提交都产生新副作用 |
| GET / PUT / DELETE 呢 | 语义上幂等，但实现仍要自己保证 |
| 创建类怎么保证 | Token 唯一 ID 前置拦截 + DB 唯一索引兜底 |
| 更新类怎么保证 | 乐观锁（version）或状态机约束 |
| 先查后插行不行 | 不行，并发下都查不到都会插，需原子约束 |
| 分布式锁能幂等吗 | 不能，只防并发不防先后重复 |
