# MQ 如何防止消息丢失，Kafka / RabbitMQ / RocketMQ 如何选型

</div>

> MQ 在哪些环节会丢消息？生产者、Broker、消费者三端各自怎么防丢？「至少一次」和「恰好一次」到底怎么理解？Kafka、RabbitMQ、RocketMQ 三大中间件在吞吐、消息模型、顺序、事务上有什么区别，实际项目里该怎么选？

### 一、这道题在考察什么

「消息不丢」是 MQ 面试的**必考核心**，但很多人的答案只停留在「手动 ack」这一句，失分点就在这里。面试官真正想确认三件事：

1. **有没有全局视角**：消息从**生产 → 存储 → 消费**是一条链，丢消息可能发生在任何一个环节，只答一个环节说明没理解完整链路。
2. **懂不懂「至少一次」的代价**：MQ 的可靠性本质是「宁可重、不可丢」——防丢要靠重试，重试就带来重复，重复又必须靠幂等兜底。能把「防丢」和「幂等」串起来，是高级和初级的区别。
3. **会不会选型**：Kafka / RabbitMQ / RocketMQ 不是「哪个更好」，而是「哪个更适合你的场景」，能说出各自的取舍才算真懂。

所以这篇文章分两层：**第一层把「不丢」的机制讲透，第二层把三大 MQ 的差异和选型讲清。**

### 二、消息在哪些环节会丢

一条消息的生命周期有三段，每段都可能丢：

| 环节 | 怎么丢的 |
|------|---------|
| **生产者 → Broker** | 网络抖动、发送超时、异步发送没等确认就以为成功 |
| **Broker 内部** | 收到消息就回 ACK 但没落盘；宕机后内存里的消息没了；单副本无冗余 |
| **Broker → 消费者** | 消费者采用**自动 ACK**，消息刚拉到手就确认，业务还没处理完就崩溃 |

> 核心认知：**可靠性是一条链，任何一环松了，整条链都不保证。** 要「不丢」，三端都要做防护。

### 三、三道防线：三端各自怎么防

</div>

#### ① 生产者：发送确认 + 失败重试

生产者的目标：**确保消息真的被 Broker 接收了，才认为发送成功**。

| MQ | 机制 | 关键点 |
|----|------|--------|
| Kafka | `acks` 参数 | `acks=all`（所有 ISR 副本都写入才返回成功，最可靠）；`acks=1`（leader 写入即可）；`acks=0`（不等确认，最快但可能丢） |
| RocketMQ | 同步发送 + 重试 | `SYNC` 同步发送，失败自动重试；别用 `ONEWAY`（发完不管，会丢） |
| RabbitMQ | 发送方确认（confirm） | 开启 publisher confirm，Broker 持久化后才回 ack |

```java
// Kafka 示例：acks=all + 重试
props.put("acks", "all");
props.put("retries", 3);           // 失败重试
props.put("enable.idempotence", true);  // 配合幂等，防重试导致重复
```

#### ② Broker：持久化 + 副本冗余

Broker 的目标：**消息落盘，且有多副本，单点宕机不丢**。

| MQ | 持久化 / 副本机制 |
|----|------------------|
| Kafka | 消息写入分区日志文件，`replication.factor` 设置副本数（≥2），`min.insync.replicas` 保证至少 N 个副本同步 |
| RocketMQ | 同步刷盘（`SYNC_FLUSH`）+ 主从同步复制，消息写文件并同步副本 |
| RabbitMQ | 消息与队列声明 `durable=true`（持久化），配合镜像队列（Mirror Queue）多副本 |

> 关键点：**「收到即回 ACK」和「落盘再回 ACK」是两回事**。要防丢，必须让 Broker 在**持久化完成后**才确认。

#### ③ 消费者：手动 ACK + 幂等兜底

消费者的目标：**业务真正处理成功，才确认消费**。

```java
// 关闭自动 ack，业务处理成功后再手动确认
// Kafka：enable.auto.commit=false，处理完手动 commit
// RabbitMQ：autoAck=false，basicAck 手动确认
// RocketMQ：消费返回 CONSUME_SUCCESS 才算成功，否则重投
```

这里有个绕不开的矛盾：

```
防丢 → 失败要重投 → 重投会产生重复 → 必须靠「业务幂等」兜底
```

所以「消息不丢」和「幂等」是**一对孪生问题**——面试里主动把这两者连起来讲，是明显加分项（幂等具体方案见本分类「请求的幂等性如何保证」一文）。

### 四、投递语义：从「至少一次」到「恰好一次」

MQ 的投递保证分三档，理解它们是理解「防丢」的理论基础：

| 语义 | 含义 | 怎么做到 | 代价 |
|------|------|---------|------|
| **至多一次（at-most-once）** | 消息可能丢，但绝不重复 | 生产者不重试、消费者自动 ack | 丢消息 |
| **至少一次（at-least-once）** | 消息绝不丢，但可能重复 | 三端全防 + 失败重投 | 重复，需幂等 |
| **恰好一次（exactly-once）** | 既不丢也不重复 | 至少一次 + 幂等（或事务） | 复杂度最高 |

> 关键认知：**MQ 本身默认只能做到「至少一次」，做不到「恰好一次」**。真正的「恰好一次」是「至少一次」投递 + **业务端幂等**共同实现的。这是面试高频追问点——别张口就说「Kafka 能恰好一次」，要补一句「是借助事务/幂等实现的」。

### 五、三大 MQ 对比与选型

  <img src="../../assets/diagrams/mq-message-reliability/mq-comparison.svg" alt="Kafka、RabbitMQ、RocketMQ 在吞吐、消息模型、顺序、事务、场景五个维度的对比">
</div>

#### 一句话定位

| MQ | 出身 | 定位 |
|----|------|------|
| **Kafka** | LinkedIn → Apache | **高吞吐的分布式流平台**，为海量日志/事件而生 |
| **RabbitMQ** | Rabbit → VMware | **功能全面、路由灵活的通用消息队列**，AMQP 标准 |
| **RocketMQ** | 阿里 → Apache | **面向金融级的分布式消息中间件**，重可靠性和事务 |

#### 核心差异

| 维度 | Kafka | RabbitMQ | RocketMQ |
|------|-------|----------|----------|
| **吞吐量** | 极高（百万级 TPS） | 中（万级） | 高（十万级） |
| **消息模型** | Topic + 分区 + 消费组 | Exchange 路由 + Queue 绑定 | Topic + Tag + 消费组 |
| **消息顺序** | 分区内有序 | 难保证（多消费者下） | 队列内严格有序 |
| **事务消息** | 需自行实现 | 无原生支持 | **原生事务消息** |
| **延迟/定时** | 弱（新版有改进） | 插件实现 | **原生定时/延迟消息** |
| **成熟生态** | 大数据生态最强 | 通用、文档好 | 阿里系/电商金融最强 |
| **运维复杂度** | 依赖 ZK（新版可去掉） | 轻量、易部署 | 组件较多（NameServer、Broker、Dashboard） |

#### 选型建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| 日志采集、埋点、大数据流 | **Kafka** | 吞吐第一，配合 Flink/Spark 生态 |
| 业务解耦、复杂路由、量不大 | **RabbitMQ** | 灵活 Exchange、易运维、文档好 |
| 金融交易、电商订单、要事务/顺序 | **RocketMQ** | 原生事务消息、严格顺序、高可靠 |
| 中小团队、快速落地 | **RabbitMQ** 或 **RocketMQ** | 运维负担比 Kafka 轻 |

> 选型核心看四点：**吞吐量、可靠性要求、消息模型复杂度、是否需要事务/顺序/定时**。不要纠结「哪个技术更牛」，而要问「我的场景最需要什么」。

### 六、总结与面试答题框架

| 问题 | 答案要点 |
|------|---------|
| 消息在哪几个环节会丢 | 生产→Broker、Broker 内部、Broker→消费 三段 |
| 生产者怎么防 | 发送确认（acks=all / SYNC / confirm）+ 失败重试 |
| Broker 怎么防 | 持久化落盘 + 多副本冗余 |
| 消费者怎么防 | 手动 ACK，业务处理成功才确认 |
| 防丢的代价 | 重试带来重复，需幂等兜底 |
| 至少一次 vs 恰好一次 | MQ 默认至少一次；恰好一次 = 至少一次 + 幂等 |
| 三大 MQ 怎么选 | 大数据流 Kafka、复杂路由 RabbitMQ、金融事务 RocketMQ |

**面试组织答案的建议顺序**：先框定「三段链路」的全局视角 → 逐段讲防丢机制（生产者确认、Broker 持久化副本、消费者手动 ack）→ 点出「防丢靠重试、重试需幂等」的代价闭环 → 再落到三大 MQ 的选型差异。**能讲清「不丢」与「幂等」的因果链，并把选型落到具体场景，是这道题从及格到高分的关键。**
