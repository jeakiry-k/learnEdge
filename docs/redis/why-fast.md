# Redis 为什么这么快：设计与实现

<div class="question-tags">
  <span class="question-tag">Redis</span>
  <span class="question-tag">性能</span>
  <span class="question-tag">设计</span>
</div>

> Redis 为什么能做到单机 10 万+ QPS？它是如何设计实现的？这些设计思想在平时开发中有哪些可以借鉴？

### 一、Redis 到底有多快

Redis 官方的基准测试（redis-benchmark）里，单机轻松跑到 **10 万+ QPS**，很多场景能到 20 万。对比之下，MySQL 单机通常几千 QPS。这个数量级的差距，来自一系列设计上的「取舍」——它不是靠蛮力堆硬件，而是靠**极致的简单和针对性优化**。

### 二、根本原因：纯内存操作

Redis 的数据**全部放在内存**里，读写不经过磁盘（持久化是异步的、可选的）。这是快的第一前提：

```
MySQL：查询 → 磁盘 IO → 返回（毫秒级，磁盘是瓶颈）
Redis：查询 → 内存 → 返回（微秒级，几乎无 IO）
```

内存访问比磁盘快几个数量级。**「快」的第一性原理：能放内存就放内存，别碰磁盘。**

### 三、单线程模型：用简单换极致

Redis 6.0 之前，**命令的执行是完全单线程**的——一个线程处理所有请求。这看起来反直觉，却是它快的核心原因之一：

| 多线程的问题 | 单线程的收益 |
|-------------|-------------|
| 线程切换开销 | 无上下文切换，CPU 全用于干活 |
| 锁竞争、死锁 | 无需加锁，天然原子性 |
| 共享数据结构复杂 | 数据结构无需考虑并发，实现更简单高效 |
| 调试困难 | 单线程执行顺序可预测 |

```
单线程为什么反而快？

Redis 的瓶颈不在 CPU，而在网络 IO 和内存访问
→ 单线程避免锁和切换，CPU 反而利用得更充分
→ 每个命令都很轻（内存操作），单线程完全处理得过来
```

> 关键点：**单线程 + 内存操作 = 每条命令执行极快**。既然每条命令都是微秒级，单线程排队也不会成为瓶颈，反而省掉了多线程的一切开销。

### 四、IO 多路复用：一个线程扛住海量连接

单线程怎么同时服务成千上万个客户端？答案是 **IO 多路复用（IO Multiplexing）**：

```
传统阻塞模型：
  每个连接一个线程 → 10000 连接 = 10000 线程 → 大量切换和内存

Redis 的 epoll：
  一个线程 + epoll 监听所有连接的 socket
  → 哪个连接有数据来了，才处理哪个
  → 10000 个连接一个线程就能扛
```

Linux 上用 `epoll`，这是像 Nginx、Netty 一样的高性能网络框架的通用做法：

```
epoll 监听 10000 个 socket
  → 平时这些连接大多空闲，不占 CPU
  → 只有真正有请求到达的连接才会被"激活"处理
  → 单线程在事件间快速轮转，看起来"同时"处理了所有连接
```

### 五、精心设计的数据结构

Redis 的每种数据结构都针对性地做了优化，追求**内存紧凑 + 操作高效**：

| 数据结构 | 底层实现优化 | 亮点 |
|---------|-------------|------|
| String | SDS（简单动态字符串） | 记录长度，`O(1)` 取长度；预分配减少扩容 |
| List | 压缩列表 / 双向链表 | 小数据用紧凑的 ziplist，省内存 |
| Hash | 压缩列表 / 哈希表 | 哈希表采用**渐进式 rehash**，扩容不阻塞 |
| ZSet | 跳表 + 哈希表 | 跳表 `O(log n)` 范围查询 |
| Set | 整数集合 / 哈希表 | 纯整数用紧凑的 intset |

**渐进式 rehash** 是经典设计：哈希表扩容时，不一次性搬完所有数据（否则会卡顿），而是每次操作搬一部分，把大任务拆小，避免毛刺。

### 六、简洁到极致的响应协议

Redis 使用 **RESP 协议**（REdis Serialization Protocol），文本形式，简单得夸张：

```
客户端发送：*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$4\r\ntom\r\n
             ↑ 3个参数   ↑SET   ↑name    ↑tom

服务端回复：+OK\r\n
```

相比 HTTP 的大堆头信息、XML/JSON 的层层包装，RESP 几乎零开销。**协议越简单，解析越快。**

### 七、6.0 之后的多线程：只优化瓶颈

Redis 6.0 引入了多线程，但很克制——**命令执行仍是单线程**，只有网络 IO（读写 socket）多线程化：

```
6.0 之前：
  单线程既要读网络数据，又要执行命令

6.0 之后：
  多个 IO 线程负责读/写 socket（并行）
  → 但命令的执行仍然只有一个线程串行
  → 既利用了多核的 IO 能力，又保持了单线程命令的原子性
```

> 这说明一个工程智慧：**优化要精准打击真正的瓶颈**。Redis 的瓶颈在 IO，就只把 IO 改成多线程，核心逻辑保持单线程不动。

### 八、开发中可借鉴什么

1. **能缓存就缓存**：热点数据、计算结果放进内存缓存，别反复查库/重算。这是 Redis 给业务最大的启发。

2. **用简单换性能**：单线程模型告诉我们——如果一把锁/一次切换就能拖慢整个系统，不如设计成无锁、无共享。**高并发不一定靠多线程，无锁单线程往往更快。**

3. **IO 多路复用思想**：像 Netty、Nginx 一样，用「一个线程 + 事件循环」处理海量长连接，而不是「一个连接一个线程」。Java 里可以借鉴 Reactor 模型。

4. **数据结构要匹配场景**：Redis 为不同数据形态选不同底层结构（整数用 intset、范围查询用跳表）。写代码也一样，选对容器（ArrayList vs LinkedList、HashMap vs TreeMap）比盲目优化更重要。

5. **大任务拆小、平摊成本**：渐进式 rehash 的思想——扩容/重建这类重活，拆到每次操作里做一点，避免一次性阻塞。对应到业务就是：大表迁移分片做、大文件分块处理、缓存预热分批导。

6. **协议/接口保持简单**：简单协议解析快、排错快。内部服务间通信，能用轻量协议就别上重型序列化。

```
借鉴清单：
  ① 内存缓存      → 减少慢 IO
  ② 无锁单线程    → 减少切换与锁竞争
  ③ 事件驱动      → 一个线程扛海量连接
  ④ 匹配的数据结构 → 从源头选对容器
  ⑤ 渐进式处理    → 大任务拆小，避免毛刺
```

### 九、总结

| 问题 | 答案 |
|------|------|
| 为什么快 | 纯内存 + 单线程 + IO 多路复用 + 高效数据结构 + 简洁协议 |
| 单线程为什么反而快 | 内存操作极快，瓶颈不在 CPU，省掉锁和切换 |
| 单线程怎么扛高并发 | IO 多路复用（epoll）事件驱动 |
| 6.0 后多线程动了什么 | 只动网络 IO，命令执行仍单线程 |
| 最值得借鉴的设计 | 用简单换性能、无锁单线程、渐进式 rehash、精准优化瓶颈 |
